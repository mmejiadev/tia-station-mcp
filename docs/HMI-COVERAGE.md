# HMI coverage — classic WinCC and WinCC Unified, all of it

Written 2026-10-20, when the user set the bar for HMI: **everything** both kinds of screen can do —
draw, create tags and memory bits, animate, move, react to events — and add every device that
carries a screen: a PLC, a PC station, a Comfort panel, a Unified panel. This document is the
checklist that bar is measured against. Waves D (classic) and U (Unified) in `ROADMAP.md` point here
for the item-by-item detail.

## How the list was made, and why it can be trusted

Not from memory. Three sources, each read on 2026-10-20:

1. **The Openness API itself.** `PublicAPI\V20\Siemens.Engineering.xml` documents about 600 HMI
   types. Every Unified shape, widget, control, dynamization and event kind below is a type in it.
2. **The class corpus** (`C:\Users\mamem\tools\class-corpus`, outside the repository): the classic
   screens exported from the year's projects, counted element by element, and the HMI and PC devices
   the class configured.
3. **What this repository already does**, read from `src/TiaMcpServer.Portable/Hmi/`.

## The one fact that shapes the whole plan

**Unified has an object model; classic WinCC does not.** In Unified, a rectangle is an `HmiRectangle`
with properties Openness can set one by one, and every property can be enumerated by code, so
coverage can be proven exhaustively. In classic WinCC, Openness has no screen-item objects at all: a
screen enters and leaves TIA Portal only as XML, and the XML schema is not shipped. So for classic
WinCC, "knowing how to draw X" means knowing the XML of X, and **the XML of a feature is only known
once it has been measured**: drawn once in TIA Portal by hand, exported, generated by the server,
imported, compiled, and exported again identical. A feature nobody has measured is not supported,
however plausible its XML looks.

That is why the classic half has a **feature atlas** (row C0 below): one reference project with one
screen per feature, made by hand once, exported, and kept as the ground truth and the regression
test of the generator. Made from scratch rather than from class material, its exports are ordinary
test assets.

## 1. Devices — adding what carries a screen, and connecting it

Measured 2026-10-20: a PC station is not a device but a rack, `System:Rack.PC`, and the HMI runtime
is a module plugged into it with an **empty** name. A real name fails with "The name could not be
set", `null` fails with "The argument 'name' may not be null", and TIA Portal names the runtime
`HMI_RT_1` itself, read-only. One failed plug followed by another once took TIA Portal down, so
`AddPcStation` accepts only the two measured runtimes. A PowerShell probe hid the difference between
`null` and empty: PowerShell passes `$null` to a `string` parameter as `""`.

## Order

Devices first (H), because nothing else can be measured without a panel to put it on; then tags (T),
because every animation needs one; then drawing (C, U-S, U-W, U-C), animation and movement (A),
events (E), runtime features (R), and simulation (S) last, because it needs everything before it.
Classic and Unified advance side by side through each step, so neither falls behind the other.
