# Web platform — design

Status: **proposal, 2026-10-03.** Nothing here is built yet. Decisions the user has taken are marked
*decided*; everything else is a proposal to be agreed before the phase that needs it starts.

## What it is for

A web application where engineers, their teacher or supervisor, and their colleagues see what has
happened to their TIA Portal projects: every change the MCP server made, every compilation and its
messages, the last known state of each project, and a description of it, organised in folders.

Who uses it:

- **The engineer** whose machine runs TIA Portal and the MCP server. Their projects are the data.
- **A supervisor** — the teacher in class, a lead engineer at a company — who reviews that work.
- **Colleagues**, who read it.

## Principles

These come first because every later choice is checked against them.

1. **The web never writes to TIA Portal or to a controller.** Writes go through the MCP server and
   its governance, and nowhere else. The web reads what happened and organises it: descriptions,
   folders, images and profiles are the web's own data and are edited there; a block, a tag or a
   device parameter never is. A web page that could change a PLC program would be a second write
   path with none of the guards, reachable from a network.
2. **`audit.jsonl` stays the source of truth.** The database is an index built from it and from the
   other files the server writes. If the database is lost, it is rebuilt from those files; if the two
   disagree, the files win. The audit trail is a hash chain, and its guarantees are not moved into a
   database that an administrator could edit row by row.
3. **The import is idempotent.** Importing the same files twice changes nothing, so it can run on a
   timer and after every crash without anybody deciding whether it is safe.
4. **Ask for as little personal data as the purpose needs.** Every profile field beyond name and
   e-mail is optional. This is GDPR's data-minimisation principle, and a company reviewing the tool
   will check it.
5. **Anything generated by AI says so** until a person has reviewed it.

## Where it runs

The data is born on the engineer's machine, next to TIA Portal. The readers are elsewhere: the
teacher at home, a colleague in another office. That gap decides the architecture.

```text
 Engineer's machine (Windows, TIA Portal)            Server (company or cloud)
 ┌──────────────────────────────────────┐            ┌──────────────────────────────┐
 │ TiaMcpServer ──writes──► audit.jsonl │            │  Web API (auth, read model)  │
 │                         compilations │  HTTPS     │        │                     │
 │                         backups/     │ ─────────► │   PostgreSQL                 │
 │ Station agent (harness) ─ reads, ────┘  signed    │        │                     │
 │   verifies the chain, pushes batches   batches    │  Web UI (dashboard)          │
 └──────────────────────────────────────┘            └──────────────────────────────┘
```

- **Station agent.** Part of `harness/`. Reads the files, verifies the audit chain, and pushes new
  entries in batches over HTTPS, authenticated with a token issued to that station. Push rather than
  pull, so the engineer's machine never has to accept a connection from a network.
- **Web API and UI.** A new package, `platform/`, separate from `harness/`. The harness API listens
  on the loopback address on purpose (see `harness/src/apiServer.ts`), and a public server living in
  the same package would make that guarantee one configuration flag away from breaking.
- **For development everything runs on one machine**: PostgreSQL in Docker Desktop (*decided*), the
  API and UI on `localhost`. Sign-in with Google and GitHub works against `localhost` during
  development; for colleagues to reach it, the server needs a stable HTTPS address, which is the
  deployment question below.

Access by the teacher and colleagues is *decided*; where the server lives is not.

## Components

| Part | Choice | Why |
|---|---|---|
| Database | PostgreSQL 18, in Docker for development | *Decided.* Same engine in development and production. Port 5433 on the host, because a native PostgreSQL 18 already holds 5432 on the development machine. |
| Schema and queries | Drizzle ORM | *Decided.* TypeScript, schema as code, migrations in the repository. |
| Authentication | Better Auth | *Decided.* TypeScript, Drizzle adapter, OAuth, organisations and roles. |
| Sign-in providers | Google, GitHub | *Decided.* E-mail and password can be added later without a migration. |
| Web UI | The existing `dashboard/` (React, Vite, Tailwind, Radix) | It already has the views, the palette and the copilot. |
| Local development | `docker-compose.yml` at the root | One command brings up the database, with a named volume and the password in `.env`, never in Git. |

## Data model

Names are the Drizzle table names. Every table has `id`, `created_at` and `updated_at` unless noted.

**People and organisations**

- `user`, `session`, `account`, `verification` — owned by Better Auth.
- `profile` — one per user: `display_name`, `job_title` (engineer, technician, student, teacher…),
  `specialty`, `company`, `bio`, `avatar_url`, `languages`, `certifications`. All optional.
- `organization`, `membership(user, organization, role)` — role is `viewer`, `engineer`,
  `supervisor` or `admin`.
- `tia_identity(user, tia_author, station, status)` — "I am `mamem` in TIA Portal". `status` is
  `claimed` until an admin or supervisor confirms it; until then the projects show the TIA name, not
  the person. Without the confirmation step anybody could claim anybody's projects.

**Where the data comes from**

- `station(organization, name, token_hash, last_seen_at)` — an engineer's machine.

**Projects**

- `folder(organization, parent, name)` — a tree; `parent` is null at the top.
- `project(organization, folder, station, tia_path, name, tia_author, tia_created_at,
  tia_modified_at, tia_modified_by)` — what TIA Portal says about the project.
- `project_description(project, body, source, model, reviewed_by, reviewed_at)` — `source` is
  `manual` or `ai`; an AI one shows as such until `reviewed_by` is set.
- `project_image(project, kind, storage_key, caption)` — `kind` is `upload` or a generated drawing
  (`network`, `rack`, `grafcet`).
- `tag(organization, name)`, `project_tag(project, tag)`.

**What happened** (imported, never edited from the web)

- `change(project, plan_id, timestamp, mode, tool, target, outcome, detail, backup_path, origin,
  entry_hash)` — one row per audit entry. Unique on `entry_hash`, which is what makes the import
  idempotent.
- `compilation(project, software_path, timestamp, error_count, warning_count, outcome)` and
  `compilation_message(compilation, severity, path, text)`.
- `project_snapshot(project, taken_at, blocks, devices, tags)` — the last known state, as JSON, for
  showing a project while TIA Portal is closed. Optional, phase 4.

## What the server has to add

Compiling already goes through the guard, so each compilation is in the audit trail with its
outcome — but not with its error and warning counts or its messages, and those are what the
compilation view shows. **The C# server writes `compilations.jsonl`** next to the audit trail, one
line per compilation with the counts and messages. A separate file rather than a longer audit
`detail`: the audit chain records decisions, and a hundred compiler messages in it would make it
harder to read for what it is for.

The project's own attributes — author, creation and modification — are read through Openness and
written to a `projects.jsonl` the same way when a project is opened.

## Screens

- **Sidebar**, always on the left: the organisation, then the folder tree with the projects inside,
  a search box, and tags as filters. Folders can be created, renamed, nested and moved by dragging.
- **Project page**, with tabs:
  - *Summary* — description, images, author (the person when the identity is confirmed), status
    badges: compiles, warnings, errors, last backup, Study or Workshop mode.
  - *Description* — written by hand, or generated with AI on request and marked as such.
  - *Changes* — the change history, filterable, each row linking to its backup.
  - *Compilations* — the list with counts, the messages of each, and a chart over time.
  - *Hardware* — CPU, modules and network, and the generated drawings.
- **Profile** — the user's own page, and a read-only version for others.
- **Organisation** — members, roles, stations and their tokens, identity confirmations.

**Colour carries meaning, and the same meaning everywhere**: green compiles, amber has warnings,
red has errors, blue is simulation, grey is no data. Never colour alone — every status also has an
icon and a word, for colour-blind users and for printing. Light and dark themes; Catalan, Spanish
and English.

## Ideas for later

- **Side-by-side diff of a block before and after a change.** Every write is preceded by a backup,
  so both versions exist already. Probably the most valuable thing on this list.
- Supervisor approval of Workshop plans from the web. This touches the governance layer and needs
  its own safety design; it is not part of any phase below.
- A project timeline joining changes, compilations and backups.
- Global search: "which projects use `Clock_1Hz`", "who changed `FB_Station`".
- PDF report of a project or of an audit, for handing in or for a client.
- Live PLCSIM values over OPC UA (phase 9), read-only.
- Notifications: a project failing three compilations in a row, a backup that failed.

## AI descriptions

Generated only when a person asks, never automatically, with a monthly spending limit per
organisation that refuses rather than overruns. The prompt receives the project's structure — block
names, devices, tags, comments — and never the audit trail's personal data.

## Phases

1. **Foundation.** `docker-compose.yml` with PostgreSQL; the Drizzle schema and migrations in
   `platform/`; the importer for `audit.jsonl`. Done when an import of a real audit trail fills
   `change`, a second import changes nothing, and a broken chain is refused with the line that
   breaks it. **Done 2026-10-03.**
2. **Compilations.** The C# server writes `compilations.jsonl` and `projects.jsonl`; the importer
   reads them. Done when a compile through the MCP appears with its messages. **Done
   2026-10-03.**
3. **People.** Better Auth with Google and GitHub, profiles, organisations, roles, the TIA identity
   claim and its confirmation. Done when a second account sees only what its role allows. **2026-10-04: sign-in with Google
   works; roles, profiles and identity confirmation are enforced by the API and tested. What a
   second account sees is for phase 4, which has the screens to show it.**
4. **The web.** Sidebar, folders, project page, changes and compilations views. Done when the
   teacher can sign in from another machine and read a project.
5. **Extras.** AI descriptions, images and drawings, snapshots, metrics, the diff.

Each phase ships with tests, as everything in this repository does.

## Open questions

- **Where the server lives** once others need it: a machine at the institut or the company, or a
  hosted service (a PostgreSQL provider plus an application host). It decides the HTTPS address
  the sign-in providers need, and who is responsible for the data.
- Whether one organisation per class or company is enough, or whether people belong to several.
- How long changes and compilations are kept.
